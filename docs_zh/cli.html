CLI 参考

OpenSpec CLI (openspec) 终端命令的完整参考

OpenSpec CLI（openspec）提供用于项目设置、验证、状态检查和管理的终端命令。这些命令补充了在命令中记录的 AI 斜杠命令（如 /opsx:propose）。

总览

类别命令用途
设置init、update在你的项目中初始化和更新 OpenSpec
Stores（独立 OpenSpec 仓库）store setup、store register、store unregister、store remove、store list、store doctor管理 stores — 你已注册的独立 OpenSpec 仓库
健康检查doctor报告已解析根的关系健康状态
工作上下文context组装工作集（根 + 引用的 stores）
个人工作集workset create、workset list、workset open、workset remove在工具中保存和打开个人的本地工作视图
浏览list、view、show探索变更和规格
验证validate检查变更和规格的问题
生命周期archive完成已完成的变更
工作流new change、status、instructions、templates、schemas制品驱动的工作流支持
模式schema init、schema fork、schema validate、schema which创建和管理自定义工作流
配置config查看和修改设置
实用工具feedback、completion反馈和 shell 集成

人类 vs Agent 命令

大多数 CLI 命令设计用于终端中的人类使用。一些命令也通过 JSON 输出支持agent/脚本使用。

设置命令

openspec init

在你的项目中初始化 OpenSpec。创建文件夹结构并配置 AI 工具集成。

默认行为使用全局配置默认值：profile core、delivery both、workflows propose, explore, apply, sync, archive。

openspec init [path] [options]

参数：

参数必需描述
path否目标目录（默认：当前目录）

选项：

选项描述
--tools <list>非交互式配置 AI 工具。使用 all、none 或逗号分隔列表
--force自动清理遗留文件无需提示
--profile <profile>为此次初始化覆盖全局 profile（core 或 custom）

--profile custom 使用当前在全局配置中选中的工作流（openspec config profile）。

支持的工具 ID（--tools）：amazon-q、antigravity、auggie、bob、claude、cline、codex、forgecode、codebuddy、continue、costrict、crush、cursor、factory、gemini、github-copilot、iflow、junie、kilocode、kimi、kiro、lingma、vibe、oh-my-pi、opencode、pi、qoder、qwen、roocode、trae、windsurf

此列表反映 src/core/config.ts 中的 AI_TOOLS。参见支持的工具了解每个工具的技能和命令路径。

示例：

# 交互式初始化
openspec init

# 在特定目录初始化
openspec init ./my-project

# 非交互式：配置 Claude 和 Cursor
openspec init --tools claude,cursor

# 为所有支持的工具配置
openspec init --tools all

# 为此次运行覆盖 profile
openspec init --profile core

# 跳过提示并自动清理遗留文件
openspec init --force

创建的内容：

openspec/
├── specs/              # 你的规格说明（真相来源）
├── changes/            # 提议的变更
└── config.yaml         # 项目配置

.claude/skills/         # Claude Code 技能（如果选择了 claude）
.cursor/skills/         # Cursor 技能（如果选择了 cursor）
.cursor/commands/       # Cursor OPSX 命令（如果 delivery 包含命令）
... (其他工具配置)

Stores（独立 OpenSpec 仓库）

Beta。Stores 和基于它们构建的功能（references、working context、worksets）是新的；命令名称、标志、文件格式和 JSON 输出可能在版本间变化。关于从问题出发的演练，参见stores 指南。

Store 是你在此机器上注册的独立 OpenSpec 仓库——例如一个规划仓库或合约仓库。注册一个 store 让普通命令（list、show、status、validate、new change、archive 等）通过传递 --store <id> 从任何地方在其中操作。

openspec store setup

创建并注册一个本地 store。在终端中无参数时，OpenSpec 会引导用户完成设置。Agent 和脚本应传递显式输入并使用 --json。

openspec store setup [id] [options]

选项：

选项描述
--path <path>store 应该存放的文件夹（例如 ~/openspec/<id>）
--remote <url>在新 store 的 store.yaml 中记录规范远程地址
--init-git初始化 Git 仓库并带初始提交（默认）
--no-init-git跳过所有 Git 操作：不 init，不初始提交
--json输出 JSON

非交互运行（--json、脚本、agent）必须同时传递 store id 和 --path。在交互终端中，setup 会提示位置，带有一个在可见的、用户拥有的位置的可用建议（例如 ~/openspec/<id>）；它从不默认到 OpenSpec 的管理数据目录。

示例：

openspec store setup
openspec store setup team-context
openspec store setup team-context --path ~/openspec/team-context --no-init-git
openspec store setup team-context --path ~/openspec/team-context --no-init-git --json

openspec store register

注册一个现有的本地 store 文件夹。在 stores beta 期间，根可能在任何变更存在、规格被应用或变更被归档之前就注册了；在这种情况下，openspec/changes/、openspec/specs/ 和 openspec/changes/archive/ 可能在普通命令创建它们之前不存在。一个只声明 store: <id> 的配置仓库仍然是指向另一个 store 的指针，除非该指针被移除，否则不会被注册为 store 根。

openspec store register [path] [options]

选项：

选项描述
--id <id>Store id；默认为 store 元数据或文件夹名
--yes确认为一个健康的 OpenSpec 根创建 store 身份元数据
--json输出 JSON

openspec store unregister

遗忘一个本地 store 注册而不删除文件。

openspec store unregister <id> [--json]

当一个 store 被移动、克隆到其他地方，或不应该再被此机器上的 OpenSpec 显示时使用。

openspec store remove

遗忘一个本地 store 注册并删除其本地文件夹。

openspec store remove <id> [--yes] [--json]

在交互终端中，remove 在删除前显示确切的文件夹。Agent、脚本和 JSON 调用者必须传递 --yes 确认删除。OpenSpec 拒绝删除不包含匹配 store 元数据的文件夹。

openspec store list

列出本地已注册的 stores。

openspec store list [--json]
openspec store ls [--json]

openspec store doctor

检查本地 store 注册、元数据和 Git 存在性。

openspec store doctor [id] [--json]

Doctor 仅为诊断；它报告缺失的根、元数据不匹配和无效的本地注册状态而不修改 store。

从项目中引用 stores

一个项目仓库可以在 openspec/config.yaml 中声明其工作所依赖的 stores：

schema: spec-driven
references:
  - team-context

此后，该仓库中的 openspec instructions 输出（包括每个制品和 apply 表面，JSON 和人类模式）携带每个引用 store 规格的索引——规格 id、每个规格 Purpose 部分的一句话摘要，以及获取命令（openspec show <spec-id> --type spec --store <id>）。索引在每次运行时从注册的检出现场构建；规格内容从不复制到输出中。

References 是只读上下文。它们从不改变命令在哪里操作：工作留在仓库自己的根中，向引用的 store 写入仍然是显式的 --store 操作。无法解析的引用（例如，此机器上未注册的 store）在索引中降级为警告，带确切修复，指令仍然生成。openspec doctor 在一处报告引用健康状态。

记录 store 的克隆来源

一个 store 可以在其提交的身份文件中记录其规范克隆源，这样入门永远不会在"注册 store"处死路一条：

openspec store setup team-context --path ~/openspec/team-context \
  --remote git@github.com:acme/team-context.git

远程地址落在初始提交中的 .openspec-store/store.yaml 里，所以每个克隆天生就知道它。对于已存在的 store，手动编辑 store.yaml 并提交。store doctor 显示记录的远程地址（和检出观察到的 Git origin）；setup/register 的共享指导会提到它；register 在机器本地注册中记录检出的 origin。

引用声明也可以携带克隆源，这样还没有 store 的队友获得一个完整的、可粘贴的修复（git clone <remote> <path> && openspec store register <path> --id <id>）：

references:
  - { id: team-context, remote: "git@github.com:acme/team-context.git" }

记录远程地址不是同步：OpenSpec 从不自行克隆、拉取或推送。

声明默认 store

一个规划完全外置的仓库——没有本地 openspec/specs/ 或 openspec/changes/——可以一次性声明其 store 而不必在每个命令上传递 --store：

# openspec/config.yaml（openspec/ 下的唯一文件）
store: team-context

此后普通命令自动解析到声明的 store；根横幅和 JSON root 块报告 source: "declared" 带 store id，打印的提示仍携带 --store <id>。声明是回退，从不覆盖：显式 --store 总是优先，有实际规划文件夹的目录忽略指针（带警告）。要将指针仓库转换为本地 OpenSpec 根，移除 store: 行并运行 openspec init——init 在声明存在时拒绝搭建脚手架。

Doctor（关系健康）

一个只读问题，一处：OpenSpec 根是否健康，它引用的 stores 在此机器上是否可用？

openspec doctor [--store <id>] [--json]

报告区分根健康、store 元数据健康（包括记录的远程和检出 origin 不一致时的说明），以及引用健康（指令显示的相同诊断，带未解析引用的克隆修复）。任何严重程度的健康发现都退出 0——agent 读取 status 数组；只有命令失败（无根、未知 store）退出 1。Doctor 从不克隆、同步或修复。要获取组装的集合本身而非其健康状态，使用 openspec context。

工作上下文（组装的集合）

此工作通过 OpenSpec 声明关联的所有内容，在一个工作集中：OpenSpec 根和它引用的 stores。

openspec context [--store <id>] [--json] [--code-workspace <path> [--force]]

JSON 摘要是 agent 可消费的（每个可用的引用 store 携带其获取配方；未解析的成员携带相同的修复指令和 doctor 显示）。--code-workspace 额外写入一个 VS Code 工作区文件，包含根加上可用的引用 stores（ref:<id> 文件夹）——这是此命令执行的唯一写入操作，如果文件存在则无 --force 拒绝。不可用的成员被报告，从不猜测。

"工作上下文"是组装的集合；openspec/config.yaml 中的 context: 字段是注入到指令中的项目背景——两件不同的东西。openspec doctor 回答集合是否健康；openspec context 回答集合是什么。

个人工作集

Beta。Worksets 是新 beta 表面的一部分；命令、标志和文件格式可能在版本间变化。关于演练，参见stores 指南。

Workset 是一个个人的、命名的视图，包含你一起工作的文件夹——一个规划根加上你选择的其他任何东西——保存在你的机器上并按名称在你的工具中重新打开。它纯粹是本地的：从不提交、从不共享、从不从声明推导，删除一个从不触及成员文件夹。

openspec workset create [name] [--member <path> | --member <name>=<path>]... [--tool <id>] [--json]
openspec workset list [--json]
openspec workset open <name> [--tool <id>]
openspec workset remove <name> [--yes] [--json]

create 运行一个简短的引导流程（或非交互地接受 --member 标志；第一个成员是主要的——会话从那里开始）。open 启动选择的工具：编辑器（VS Code、Cursor）打开一个包含每个成员的窗口并返回；CLI agent（Claude Code、codex）接管此终端作为带每个成员附加的会话，没有预填提示，在你退出时结束。打开时缺失的成员文件夹会被跳过并注明；其余的正常打开。保存的工具偏好可通过每次打开的 --tool 覆盖。

支持新工具是配置，不是代码。每个工具是两种启动风格之一——workspace-file（用生成的 .code-workspace 启动）或 attach-dirs（每个成员一个 attach 标志）——全局 config.json 中的 openers 键（用 openspec config edit 打开）按字段添加工具或调整内置工具：

{
  "openers": {
    "zed": { "style": "workspace-file" },
    "claude": { "attach_flag": "--dir" }
  }
}

所有 workset 状态存在于全局数据目录的 worksets/ 文件夹下（保存的视图加上生成的 <name>.code-workspace 文件，每次打开时重新生成）；删除该文件夹会移除所有痕迹。

生命周期命令

openspec archive

归档已完成的变更并将增量规格合并到主规格。

openspec archive [change-name] [options]

参数：

参数必需描述
change-name否要归档的变更（省略则提示）

选项：

选项描述
-y, --yes跳过确认提示
--skip-specs跳过规格更新（用于基础设施/工具/仅文档变更）
--no-validate跳过验证（需要确认）

示例：

# 交互式归档
openspec archive

# 归档特定变更
openspec archive add-dark-mode

# 无提示归档（CI/脚本）
openspec archive add-dark-mode --yes

# 归档不影响规格的工具变更
openspec archive update-ci-config --skip-specs

它的作用：

  1. 验证变更（除非 --no-validate）
  2. 提示确认（除非 --yes）
  3. 将增量规格合并到 openspec/specs/
  4. 将变更文件夹移至 openspec/changes/archive/YYYY-MM-DD-<name>/

工作流命令

这些命令支持制品驱动的 OPSX 工作流。它们对人类检查进度和 agent 确定下一步都很有用。

openspec new change

在解析的 OpenSpec 根中创建变更目录和可选的签入元数据。

openspec new change <name> [options]

变更名称必须使用小写 kebab-case。以小写字母开头，然后包含小写字母、数字和单个连字符。不能以数字开头，不能包含空格、下划线、大写字母、连续连字符或前后连字符。包含外部工单 ID 时，用一个词前缀，例如 ticket-123-add-notifications 而非 123-add-notifications。

选项：

选项描述
--description <text>添加到 README.md 的描述
--goal <text>随变更存储的可选目标元数据
--schema <name>使用的工作流模式
--store <id>用作 OpenSpec 根的 store id（store 是你已注册的独立 OpenSpec 仓库）
--json输出 JSON

示例：

openspec new change add-billing-api
openspec new change add-billing-api --store team-context --json

openspec instructions

获取创建制品或应用任务的增强指令。AI agent 用于了解下一步创建什么。

openspec instructions [artifact] [options]

参数：

参数必需描述
artifact否制品 ID：proposal、specs、design、tasks 或 apply

选项：

选项描述
--change <id>变更名称（非交互模式下必需）
--schema <name>模式覆盖
--json输出为 JSON

特殊情况：使用 apply 作为制品获取任务实现指令。

示例：

# 获取下一个制品的指令
openspec instructions --change add-dark-mode

# 获取特定制品指令
openspec instructions design --change add-dark-mode

# 获取 apply/实现指令
openspec instructions apply --change add-dark-mode

# JSON 供 agent 消费
openspec instructions design --change add-dark-mode --json

输出包括：

  • 制品的模板内容
  • 来自配置的项目上下文
  • 来自依赖制品的内容
  • 来自配置的按制品规则

模式命令

用于创建和管理自定义工作流模式的命令。

openspec schema init

创建一个新的项目本地模式。

openspec schema init <name> [options]

参数：

参数必需描述
name是模式名称（kebab-case）

选项：

选项描述
--description <text>模式描述
--artifacts <list>逗号分隔的制品 ID（默认：proposal,specs,design,tasks）
--default设为项目默认模式
--no-default不提示设为默认
--force覆盖现有模式
--json输出为 JSON

示例：

# 交互式模式创建
openspec schema init research-first

# 非交互式指定制品
openspec schema init rapid \
  --description "Rapid iteration workflow" \
  --artifacts "proposal,tasks" \
  --default

创建的内容：

openspec/schemas/<name>/
├── schema.yaml           # 模式定义
└── templates/
    ├── proposal.md       # 每个制品的模板
    ├── specs.md
    ├── design.md
    └── tasks.md

配置命令

openspec config

查看和修改全局 OpenSpec 配置。

openspec config <subcommand> [options]

子命令：

子命令描述
path显示配置文件位置
list显示所有当前设置
get <key>获取特定值
set <key> <value>设置值
unset <key>移除键
reset重置为默认
edit在 $EDITOR 中打开
profile [preset]交互式或通过预设配置工作流 profile

示例：

# 显示配置文件路径
openspec config path

# 列出所有设置
openspec config list

# 获取特定值
openspec config get telemetry.enabled

# 设置值
openspec config set telemetry.enabled false

# 显式设置字符串值
openspec config set user.name "My Name" --string

# 移除自定义设置
openspec config unset user.name

# 重置所有配置
openspec config reset --all --yes

# 在编辑器中编辑配置
openspec config edit

# 用基于动作的向导配置 profile
openspec config profile

# 快速预设：切换工作流到 core（保持交付模式）
openspec config profile core

openspec config profile 以当前状态摘要开始，然后让你选择：

  • 更改交付 + 工作流
  • 仅更改交付
  • 仅更改工作流
  • 保持当前设置（退出）

如果你保持当前设置，不会写入任何更改也不会显示更新提示。如果没有配置更改但当前项目文件与你的全局 profile/交付不同步，OpenSpec 会显示警告并建议 openspec update。按 Ctrl+C 也会干净地取消流程（无堆栈跟踪）并退出代码 130。在工作流清单中，[x] 表示该工作流在全局配置中已选中。要将这些选择应用到项目文件，运行 openspec update（或在项目内时选择"现在将更改应用到此项目？"）。

交互式示例：

# 仅交付更新
openspec config profile
# 选择：仅更改交付
# 选择交付：仅 Skills

# 仅工作流更新
openspec config profile
# 选择：仅更改工作流
# 在清单中切换工作流，然后确认

实用工具命令

openspec feedback

提交关于 OpenSpec 的反馈。创建一个 GitHub issue。

openspec feedback <message> [options]

参数：

参数必需描述
message是反馈消息

选项：

选项描述
--body <text>详细描述

要求：必须安装并认证 GitHub CLI（gh）。

示例：

openspec feedback "Add support for custom artifact types" \
  --body "I'd like to define my own artifact types beyond the built-in ones."

openspec completion

管理 OpenSpec CLI 的 shell 补全。

openspec completion <subcommand> [shell]

子命令：

子命令描述
generate [shell]输出补全脚本到 stdout
install [shell]为你的 shell 安装补全
uninstall [shell]移除已安装的补全

支持的 shell：bash、zsh、fish、powershell

示例：

# 安装补全（自动检测 shell）
openspec completion install

# 为特定 shell 安装
openspec completion install zsh

# 生成脚本用于手动安装
openspec completion generate bash > ~/.bash_completion.d/openspec

# 卸载
openspec completion uninstall
