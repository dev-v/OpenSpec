示例与配方

真实变更，从开始到结束

真实变更，从开始到结束。每个配方展示了你输入的命令和你会看到的回复，这样你可以将自己的情况匹配到一个模式并复制。这些使用默认的 core 命令（propose、explore、apply、sync、archive）；在扩展命令集有帮助的地方会注明。

开始前提醒：斜杠命令如 /opsx:propose 在你的 AI 助手的聊天中输入，openspec 命令在你的终端中输入。如果这是新的，先读 命令工作原理。在下面的对话中，You: 和 AI: 是聊天，以 $ 开头的行是终端。

还不确定要构建什么？如果你先用 /opsx:explore 理清思路，大多数配方会更犀利。配方 3展示了实际操作，探索优先指南做了完整说明。

配方 1：一个小功能，快速路径

何时使用：你知道自己想要什么，而且是一块独立的工作。这是最常见的配方。

整个过程只有三个命令。提议、构建、归档。

You: /opsx:propose add-logout-button

AI:  Created openspec/changes/add-logout-button/
     ✓ proposal.md — why and what
     ✓ specs/      — the new requirement and its scenarios
     ✓ design.md   — technical approach
     ✓ tasks.md    — implementation checklist
     Ready for implementation. Run /opsx:apply.

现在阅读计划。打开提案和增量规格。这是 OpenSpec 为之设计的时刻：在一个假设还是一段话时抓住它，而不是 400 行代码。如果哪里不对，直接编辑任何工件，然后继续。

You: /opsx:apply

AI:  Working through tasks...
     ✓ 1.1 Add logout button to header
     ✓ 1.2 Clear session on click
     ✓ 1.3 Add confirmation dialog
     All tasks complete!

You: /opsx:archive

AI:  Archiving add-logout-button...
     ✓ Merged specs into openspec/specs/auth/spec.md
     ✓ Moved to openspec/changes/archive/2026-06-22-add-logout-button/
     Done. Ready for the next change.

就是这样。登出行为现在是你规格的一部分，变更已连同其完整上下文归档。

配方 2：一个 Bug 修复

何时使用：某些东西坏了，你希望修复被记录为对行为的深思熟虑变更，而非一个神秘的提交。

Bug 修复的工作方式与功能完全相同。区别在于你如何构建提案：描述正确的行为，而不仅仅是"修复 Bug"。

You: /opsx:propose fix-login-redirect-loop

AI:  Created openspec/changes/fix-login-redirect-loop/
     The proposal captures the current broken behavior and the
     intended behavior. The delta spec MODIFIES the redirect
     requirement so it's now precise and testable.
     Ready for implementation.

因为修复以 MODIFIED 需求加上全新场景的方式落地，下一个人（或下一个 AI 会话）不仅看到你修复了它，还看到"正确"是什么意思。然后像往常一样 /opsx:apply 和 /opsx:archive。

提示：对于修复，一个好的场景就是用文字描述的回归测试。"GIVEN 一个未登录用户，WHEN 提交有效凭据，THEN 落在仪表板且不再被重定向。"写下这个，实现就有了明确的目标。

配方 3：在确定前探索

何时使用：你有问题但还没有方案。你不确定要构建什么，或哪种方案是对的。

先用 /opsx:explore。它是一个思考伙伴，不创建结构和工件。它阅读你的代码库并帮助你决定。

You: /opsx:explore

AI:  What would you like to explore?

You: Page loads feel slow but I don't know where the time goes.

AI:  Let me look... I found three likely culprits:
     1. Large unoptimized images on the product list
     2. Synchronous data fetching that blocks render
     3. Re-renders triggered by context changes
     Which should we tackle first?

You: The data fetching one.

You: /opsx:propose optimize-product-list-fetching

AI:  Created the change, with a proposal informed by what we just
     found. Ready for implementation.

探索在你在变更上花成本之前澄清思路。当洞见结晶时，提议，AI 会将上下文继续传递。

配方 4：同时处理两个变更

何时使用：你正在做功能中途，一个紧急修复插队了。

变更是独立的文件夹，所以并行工作不会冲突。启动修复、发布它，然后回到功能——就在你停下的地方。

You: I'm partway through add-dark-mode, but I need to fix a login bug now.

You: /opsx:propose fix-login-redirect

AI:  Created openspec/changes/fix-login-redirect/. Ready for implementation.

You: /opsx:apply

AI:  Implemented the fix. All tasks complete.

You: /opsx:archive

AI:  ✓ Archived fix-login-redirect.

You: Back to dark mode.

You: /opsx:apply add-dark-mode

AI:  Resuming add-dark-mode. Picking up at task 2.3: Update Header...

在 /opsx:apply add-dark-mode 中命名变更，就是当多个变更同时活跃时你指向特定变更的方式。因为任务在 tasks.md 中跟踪完成状态，AI 准确知道你停在哪里。

当几个变更同时完成时，扩展的 /opsx:bulk-archive 将它们一起归档并通过检查实际实现来解决规格冲突。参见 工作流。

配方 5：无行为变更的重构

何时使用：你在重构代码，外部可见行为应保持不变。

这是有趣的情况，因为纯重构不需要在规格中添加任何东西。行为契约不变；只有实现变了。所以工作存在于设计和任务中，而规格增量是空的或缺失的。

You: /opsx:propose refactor-payment-module

AI:  Created the change. The proposal states the goal (split the
     payment module, no behavior change) and the design captures
     the new structure. No spec changes, since behavior is identical.
     Ready for implementation.

当归档一个不触及规格的变更时，你可以告诉终端命令跳过规格步骤：

$ openspec archive refactor-payment-module --skip-specs

同样的标志也适用于工具配置、CI 和纯文档变更。原则是：规格描述行为，如果行为没变，规格也不应变。参见 概念。

配方 6：逐步控制（扩展命令）

何时使用：一个复杂或有风险的变更，你想在继续之前审查每个工件。

核心的 /opsx:propose 一次性草拟所有内容。当你想一步一步来时，开启扩展命令：

$ openspec config profile      # select the expanded workflows
$ openspec update              # apply them to this project

现在你可以逐步搭建和构建：

You: /opsx:new add-2fa

AI:  Created openspec/changes/add-2fa/. Ready to create: proposal.

You: /opsx:continue

AI:  Created proposal.md. Now available: specs, design.

You: /opsx:continue

AI:  Created specs/auth/spec.md. Now available: design.

当每个工件落地时审查它，自由编辑，满意后继续。当你想让剩余的一气呵成时，/opsx:ff 会快进完成剩余的规划工件。归档前，/opsx:verify 检查实现是否真正匹配规格。参见 工作流。

配方 7：动手学习整个循环

何时使用：你已经安装了 OpenSpec，想在自己的代码上感受工作流，而不是一个玩具示例。

开启扩展命令（见配方 6），然后：

You: /opsx:onboard

AI:  Welcome to OpenSpec! I'll walk you through a complete change
     using your actual codebase. Let me scan for a small, safe
     improvement we can make together...

/opsx:onboard 找到一个真实的（小）改进，为其创建变更、实现它、归档它，并讲解每一步。它需要 15 到 30 分钟，留下一个你可以保留或丢弃的真实变更。这是最温和的学习方式。参见 命令。

从终端检查你的工作

任何时候，你都可以从终端检查状态：

$ openspec list                      # active changes
$ openspec show add-dark-mode        # one change in detail
$ openspec validate add-dark-mode    # check structure
$ openspec view                      # interactive dashboard

这些是读取和检查工具。提议和构建仍通过聊天中的斜杠命令进行。完整详情见 CLI 参考。
