基础知识

一句话概括，OpenSpec 是什么？

一个轻量级层，让你和你的 AI 编码助手在编写任何代码之前，以书面形式就构建什么达成一致。

为什么我需要它？

因为 AI 助手即使错了也很自信。当需求只存在于聊天线程中时，AI 会用猜测来填补空白，而你要等到代码写完后才发现问题。OpenSpec 将达成一致的时机提前到修复成本很低的地方。完整论述参见核心概念一览。

我必须在所有事情上都用它吗？

不。在达成一致重要的地方使用它，也就是大多数非简单的工作。对于一个单字符拼写错误的修复，这个流程可能不值得，那完全没问题。

我可以在大型现有代码库上使用它吗，还是只能用于新项目？

现有代码库是主要场景。OpenSpec 是棕地优先的：你不需要预先文档化整个应用。你只为每个变更触及的部分编写规格说明，你的规格说明会随着你实际做的工作逐渐积累。有专门的指南：在现有项目中使用 OpenSpec。

它与某个 AI 工具绑定吗？

不。OpenSpec 与 25+ 助手兼容，包括 Claude Code、Cursor、Windsurf、GitHub Copilot、Gemini CLI、Codex 等。完整列表和各工具详情见支持的工具。

运行命令

我在哪里输入 /opsx:propose？

在你的 AI 助手的聊天中，而不是你的终端。这是最常见的混淆点，所以它有专门的页面：命令工作原理。简短版本：openspec ... 在终端运行，/opsx:... 在聊天中运行。

如何"启动交互模式"？

没有一个单独的模式要启动。你像平时一样打开 AI 助手，在它的聊天中输入斜杠命令。斜杠命令就是你"进入" OpenSpec 的方式。（唯一真正交互式的终端功能是 openspec view，一个浏览规格说明和变更的仪表板。）完整说明见命令工作原理。

我输入了斜杠命令但什么都没发生。为什么？

很可能你在终端而不是 AI 聊天中输入了它，或者命令还没安装。在你的项目中运行 openspec update，重启助手，然后在聊天中尝试输入 /opsx 并查看自动补全。故障排除有完整的检查清单。

为什么在一个工具中语法是 /opsx:propose，而在另一个工具中是 /opsx-propose？

每个 AI 工具展示自定义命令的方式略有不同。意图是相同的；只是标点符号不同。在聊天中输入一个斜杠，自动补全会显示你的工具期望的格式。各工具的对照表见命令工作原理。

技能和命令有什么区别？

两者都是 OpenSpec 写入的文件，以便你的助手可以运行工作流。Skills（.../skills/openspec-*/SKILL.md）是较新的跨工具标准；Commands（.../commands/opsx-*）是较早的每工具斜杠文件。你不需要选择。你只需输入斜杠命令，OpenSpec 会安装你的工具使用的那种。

工作流

如果我不确定要构建什么，应该从哪里开始？

从 /opsx:explore 开始。它是一个无风险的思考伙伴，读取你的代码库，列出选项，将模糊的问题转化为具体计划——所有这些都在任何变更或代码存在之前进行。它在默认配置中，所以总是可用的。当计划清晰后，它会交接给 /opsx:propose。这是你应该养成的最佳习惯，因为它阻止了一个急切的 AI 自信地构建错误的东西。参见探索优先。

最简单的流程是什么？

/opsx:explore (optional)   then   /opsx:propose <what you want>   then   /opsx:apply   then   /opsx:archive

探索来思考，提议来起草计划，应用来构建它，归档来收尾。当你已经确切知道你想要什么时，可以跳过探索。

/opsx:propose 和 /opsx:new 有什么区别？

/opsx:propose 是默认的一步命令：它创建变更并一次性起草所有计划产物。/opsx:new 是扩展命令集的一部分，只搭建一个空变更，让你用 /opsx:continue 逐个创建产物（或用 /opsx:ff 一次性创建）。除非你想要逐步控制，否则使用 propose。参见命令。

什么是 core 和扩展配置？

配置决定安装哪些斜杠命令。Core（默认）提供 propose、explore、apply、sync、archive。扩展集添加了 new、continue、ff、verify、bulk-archive 和 onboard，用于更精细的控制。用 openspec config profile 切换，然后用 openspec update 应用。

我需要运行 /opsx:sync 吗？

通常不需要。Sync 将变更的 delta 规格合并到你的主规格中，而 /opsx:archive 会提议帮你做。仅在你想在归档之前合并规格时手动运行 sync，例如在长时间运行的变更上。参见命令。

我已经开始了，如何编辑提议、规格或任务？

直接编辑文件即可。每个产物都是 openspec/changes/<name>/ 中的纯 Markdown，没有锁定的阶段或特殊的编辑模式。手动更改，或要求你的 AI 修改它（"将设计更新为使用队列"），然后继续。AI 总是从当前文件内容工作。完整指南：编辑与迭代变更。

我可以在实现了一部分后回去改变计划吗？

可以，随时都可以。工作流是流动的，所以审查和编辑不是你会被锁出的阶段。编辑产物，然后继续。如果你想要一个结构化的检查来确认代码是否仍然匹配计划，运行 /opsx:verify。参见编辑与迭代变更。

我手动编辑了代码。如何与规格说明协调？

在归档之前将它们重新同步，因为归档使你的规格说明成为记录的真相。如果代码现在是正确的，更新 delta 规格以匹配你发布的内容；如果规格说明是正确的，继续构建直到代码一致。/opsx:verify 会显示不匹配之处。参见编辑与迭代变更。

什么时候应该更新现有变更，什么时候应该开始新的？

当是相同工作的改进时更新。当意图根本改变或范围膨胀成不同的工作时重新开始。工作流中有决策流程图和示例。

如果我的会话上下文用完了，或者需求在实现过程中发生变化怎么办？

这正是规格说明发挥作用的地方。因为计划存在于文件中（而不仅仅在聊天历史中），你可以清除上下文，启动新的 AI 会话，用 /opsx:apply 继续；它会读取产物并从第一个未完成的任务恢复。如果需求变化，编辑产物以匹配新的现实并继续。保持干净的上下文窗口也会产生更好的结果；在实现之前清除它。

我应该将 openspec/ 文件夹提交到 git 吗？

是的。你的规格说明、活跃变更和归档是你的项目历史的一部分。像任何其他源代码一样提交它们。归档特别成为你的系统为何这样工作的持久记录。

规格说明和变更

什么放在规格说明中，什么放在设计中？

规格说明描述可观察的行为：系统做什么、它的输入、输出和错误条件。设计描述你将如何构建它：技术方案、架构决策、文件变更。如果实现在不改变外部可见行为的情况下可以改变，它应该属于设计而不是规格说明。概念详解有更深入的讨论。

什么是 delta 规格？

一种仅描述变化内容的规格说明，使用 ADDED、MODIFIED 和 REMOVED 章节，而不是重述整个规格。这是 OpenSpec 干净处理对现有系统编辑的方式。参见概念详解。

归档的变更去了哪里？

到 openspec/changes/archive/YYYY-MM-DD-<name>/，所有产物都保留。没有东西被删除；变更只是从你的活跃列表中移出。

配置和自定义

如何告诉 AI 我的技术栈？

把它放在 openspec/config.yaml 的 context: 下。该文本被注入到每个计划请求中，所以 AI 总是知道你的技术栈和约定。参见自定义配置。

我可以用英语以外的语言生成规格说明吗？

可以。在你的配置的 context: 中添加语言指令。多语言支持有几种语言的复制粘贴片段。

我可以改变工作流本身吗？

可以，用自定义 Schema。Schema 定义了存在哪些产物以及它们如何相互依赖。用 openspec schema fork spec-driven my-workflow fork 默认 Schema，然后编辑它。参见自定义配置。

模型、隐私和升级

我应该使用哪个 AI 模型？

OpenSpec 与高推理能力的模型配合效果最好。README 推荐像 Codex 5.5 和 Opus 4.7 这样的模型用于计划和实现。同时保持你的上下文窗口干净：在实现之前清除它以获得最佳结果。

OpenSpec 收集数据吗？

它收集匿名使用统计：仅命令名和版本。没有参数、路径、内容或个人数据，并且在 CI 中默认关闭。用 export OPENSPEC_TELEMETRY=0 或 export DO_NOT_TRACK=1 退出。

如何升级？

两步。升级包（npm install -g @fission-ai/openspec@latest），然后在每个项目中运行 openspec update 刷新生成的技能和命令。

如何卸载 OpenSpec？

没有卸载命令，因为它只是一个全局包加上你项目中的文件。删除包（npm uninstall -g @fission-ai/openspec>），并可选地删除 openspec/ 目录和生成的工具文件。逐步说明，包括什么可以安全保留，见安装指南：卸载。
