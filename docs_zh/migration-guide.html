迁移到 OPSX

从旧版 OpenSpec 工作流过渡到 OPSX 的完整指南

本指南帮助你从旧版 OpenSpec 工作流过渡到 OPSX。迁移设计为平滑的——你现有的工作会被保留，新系统提供更多灵活性。

有什么变化？

OPSX 用流畅的、基于动作的方法取代了旧的阶段锁定工作流。以下是关键转变：

方面 旧版 OPSX
命令 /openspec:proposal, /openspec:apply, /openspec:archive 默认：/opsx:propose, /opsx:apply, /opsx:sync, /opsx:archive（扩展工作流命令可选）
工作流 一次创建所有产物 逐步创建或一次全部创建——你的选择
回退 别扭的阶段门控 自然——随时更新任何产物
自定义 固定结构 Schema 驱动，完全可修改
配置 CLAUDE.md 带标记 + project.md 在 openspec/config.yaml 中的干净配置

理念变化：工作不是线性的。OPSX 不再假装它是。

开始之前

你现有的工作是安全的

迁移过程以保留为设计原则：

  • openspec/changes/ 中的活跃变更 — 完全保留。你可以用 OPSX 命令继续它们。
  • 已归档的变更 — 不动。你的历史保持完整。
  • openspec/specs/ 中的主规格 — 不动。这些是你的真相来源。
  • 你在 CLAUDE.md、AGENTS.md 等中的内容 — 保留。只移除 OpenSpec 标记块；你写的一切都保留。

什么会被移除

只有正在被替换的 OpenSpec 管理的文件：

内容 原因
旧版斜杠命令目录/文件 被新的技能系统取代
openspec/AGENTS.md 过时的工作流触发器
CLAUDE.md、AGENTS.md 等中的 OpenSpec 标记 不再需要

按工具的旧版命令位置（示例——你的工具可能不同）：

  • Claude Code：.claude/commands/openspec/
  • Cursor：.cursor/commands/openspec-*.md
  • Windsurf：.windsurf/workflows/openspec-*.md
  • Cline：.clinerules/workflows/openspec-*.md
  • Roo：.roo/commands/openspec-*.md
  • GitHub Copilot：.github/prompts/openspec-*.prompt.md（仅 IDE 扩展；Copilot CLI 不支持）
  • 其他（Augment、Continue、Amazon Q 等）

迁移会检测你配置了哪些工具并清理它们的旧版文件。

移除列表可能看起来很长，但这些都是 OpenSpec 原本创建的文件。你自己的内容永远不会被删除。

需要你注意的内容

有一个文件需要手动迁移：

openspec/project.md — 这个文件不会自动删除，因为它可能包含你写的项目上下文。你需要：

  1. 审查其内容
  2. 将有用的上下文移动到 openspec/config.yaml（参见下面的指导）
  3. 准备好后删除该文件

为什么我们做了这个改变：

旧的 project.md 是被动的——代理可能读它，可能不读，可能忘了读的内容。我们发现可靠性不一致。

新的 config.yaml 上下文被主动注入到每个 OpenSpec 计划请求中。这意味着你的项目约定、技术栈和规则在 AI 创建产物时总是存在的。更高的可靠性。

权衡：

因为上下文被注入到每个请求中，你会想要简洁。专注于真正重要的内容：

  • 技术栈和关键约定
  • AI 需要知道的不明显约束
  • 之前经常被忽略的规则

不要担心做到完美。我们还在这里学习什么最有效，随着实验我们会改进上下文注入的工作方式。

运行迁移

openspec init 和 openspec update 都会检测旧版文件并引导你完成相同的清理过程。使用适合你情况的那个：

  • 新安装默认使用配置 core（propose、explore、apply、sync、archive）。
  • 迁移的安装通过在需要时写入 custom 配置来保留你之前安装的工作流。

使用 openspec init

如果你想添加新工具或重新配置设置了哪些工具，运行这个：

openspec init

init 命令检测旧版文件并引导你完成清理：

Upgrading to the new OpenSpec

OpenSpec now uses agent skills, the emerging standard across coding
agents. This simplifies your setup while keeping everything working
as before.

Files to remove
No user content to preserve:
  • .claude/commands/openspec/
  • openspec/AGENTS.md

Files to update
OpenSpec markers will be removed, your content preserved:
  • CLAUDE.md
  • AGENTS.md

Needs your attention
  • openspec/project.md
    We won't delete this file. It may contain useful project context.

    The new openspec/config.yaml has a "context:" section for planning
    context. This is included in every OpenSpec request and works more
    reliably than the old project.md approach.

    Review project.md, move any useful content to config.yaml's context
    section, then delete the file when ready.

? Upgrade and clean up legacy files? (Y/n)

当你说"是"时会发生什么：

  1. 旧版斜杠命令目录被移除
  2. OpenSpec 标记从 CLAUDE.md、AGENTS.md 等中移除（你的内容保留）
  3. openspec/AGENTS.md 被删除
  4. 新技能被安装到 .claude/skills/
  5. openspec/config.yaml 以默认 Schema 创建

使用 openspec update

如果你只想迁移并刷新现有工具到最新版本，运行这个：

openspec update

update 命令也会检测并清理旧版产物，然后刷新生成的技能/命令以匹配你当前的配置和交付设置。

非交互式 / CI 环境

用于脚本化迁移：

openspec init --force --tools claude

--force 标志跳过提示并自动接受清理。

将 project.md 迁移到 config.yaml

旧的 openspec/project.md 是一个自由格式的 Markdown 文件，用于项目上下文。新的 openspec/config.yaml 是结构化的，而且——关键的是——被注入到每个计划请求中，所以你的约定在 AI 工作时总是存在的。

之前（project.md）

# Project Context

This is a TypeScript monorepo using React and Node.js.
We use Jest for testing and follow strict ESLint rules.
Our API is RESTful and documented in docs/api.md.

## Conventions

- All public APIs must maintain backwards compatibility
- New features should include tests
- Use Given/When/Then format for specifications

之后（config.yaml）

schema: spec-driven

context: |
  Tech stack: TypeScript, React, Node.js
  Testing: Jest with React Testing Library
  API: RESTful, documented in docs/api.md
  We maintain backwards compatibility for all public APIs

rules:
  proposal:
    - Include rollback plan for risky changes
  specs:
    - Use Given/When/Then format for scenarios
    - Reference existing patterns before inventing new ones
  design:
    - Include sequence diagrams for complex flows

关键区别

project.md config.yaml
自由格式 Markdown 结构化 YAML
一大段文本 分离的上下文和按产物的规则
不清楚何时使用 上下文出现在所有产物中；规则仅出现在匹配的产物中
没有 Schema 选择 显式的 schema: 字段设置默认工作流

保留什么，舍弃什么

迁移时要有选择性。问自己："AI 是否在每个计划请求中都需要这个？"

适合放在 context: 中的

  • 技术栈（语言、框架、数据库）
  • 关键架构模式（monorepo、微服务等）
  • 不明显的约束（"我们不能使用库 X 因为..."）
  • 经常被忽略的关键约定

移到 rules: 中的

  • 特定产物的格式要求（"在规格说明中使用 Given/When/Then"）
  • 审查标准（"提议必须包含回退计划"）
  • 这些仅出现在匹配的产物中，使其他请求更轻量

完全舍弃

  • AI 已经知道的通用最佳实践
  • 可以精简的冗长解释
  • 不影响当前工作的历史上下文

迁移步骤

  1. 创建 config.yaml（如果 init 还没有创建）： 
    schema: spec-driven
  2. 添加你的上下文（要精简——这会进入每个请求）： 
    context: |
  Your project background goes here.
  Focus on what the AI genuinely needs to know.
  3. 添加按产物的规则（可选）： 
    rules:
  proposal:
    - Your proposal-specific guidance
  specs:
    - Your spec-writing rules
  4. 删除 project.md，一旦你移动了所有有用的内容。

不要想太多。 从基本内容开始并迭代。如果你注意到 AI 遗漏了重要的东西，添加它。如果上下文感觉臃肿，精简它。这是一个活文档。

需要帮助？使用这个提示词

如果你不确定如何精炼你的 project.md，问你的 AI 助手：

I'm migrating from OpenSpec's old project.md to the new config.yaml format.

Here's my current project.md:
[paste your project.md content]

Please help me create a config.yaml with:
1. A concise `context:` section (this gets injected into every planning request, so keep it tight—focus on tech stack, key constraints, and conventions that often get ignored)
2. `rules:` for specific artifacts if any content is artifact-specific (e.g., "use Given/When/Then" belongs in specs rules, not global context)

Leave out anything generic that AI models already know. Be ruthless about brevity.

AI 会帮助你识别什么是必要的，什么可以精简。

新命令

命令可用性取决于配置：

默认（core 配置）：

命令 用途
/opsx:propose一步创建变更并生成计划产物
/opsx:explore无结构地思考想法
/opsx:apply从 tasks.md 实现任务
/opsx:archive完成并归档变更

扩展工作流（自定义选择）：

命令 用途
/opsx:new开始新变更脚手架
/opsx:continue创建下一个产物（一次一个）
/opsx:ff快进——一次性创建计划产物
/opsx:verify验证实现是否匹配规格
/opsx:sync将 delta 规格合并到主规格中
/opsx:bulk-archive一次归档多个变更
/opsx:onboard引导式端到端入职工作流

用 openspec config profile 启用扩展命令，然后运行 openspec update。

从旧版映射的命令

旧版 OPSX 等效
/openspec:proposal/opsx:propose（默认）或 /opsx:new 然后 /opsx:ff（扩展）
/openspec:apply/opsx:apply
/openspec:archive/opsx:archive

新功能

这些功能是扩展工作流命令集的一部分。

粒度产物创建：

/opsx:continue

基于依赖一次创建一个产物。当你想审查每个步骤时使用这个。

探索模式：

/opsx:explore

在提交变更之前与伙伴一起思考想法。

理解新架构

从阶段锁定到流畅

旧版工作流强制线性推进：

┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│   PLANNING   │ ───► │ IMPLEMENTING │ ───► │   ARCHIVING  │
│    PHASE     │      │    PHASE     │      │    PHASE     │
└──────────────┘      └──────────────┘      └──────────────┘

If you're in implementation and realize the design is wrong?
Too bad. Phase gates don't let you go back easily.

OPSX 使用动作，而不是阶段：

         ┌───────────────────────────────────────────────┐
         │           ACTIONS (not phases)                │
         │                                               │
         │     new ◄──► continue ◄──► apply ◄──► archive │
         │      │          │           │             │   │
         │      └──────────┴───────────┴─────────────┘   │
         │                    any order                  │
         └───────────────────────────────────────────────┘

依赖图

产物形成有向图。依赖是促成条件，而不是门控：

                        proposal
                       (root node)
                            │
              ┌─────────────┴─────────────┐
              │                           │
              ▼                           ▼
           specs                       design
        (requires:                  (requires:
         proposal)                   proposal)
              │                           │
              └─────────────┬─────────────┘
                            │
                            ▼
                         tasks
                     (requires:
                     specs, design)

当你运行 /opsx:continue 时，它会检查什么准备好了并提供下一个产物。你也可以按任何顺序创建多个就绪的产物。

技能 vs 命令

旧版系统使用特定工具的命令文件：

.claude/commands/openspec/
├── proposal.md
├── apply.md
└── archive.md

OPSX 使用新兴的技能标准：

.claude/skills/
├── openspec-explore/SKILL.md
├── openspec-new-change/SKILL.md
├── openspec-continue-change/SKILL.md
├── openspec-apply-change/SKILL.md
└── ...

技能被多个 AI 编码工具识别，并提供更丰富的元数据。

继续现有变更

你进行中的变更与 OPSX 命令无缝协作。

有一个来自旧版工作流的活跃变更？

/opsx:apply add-my-feature

OPSX 读取现有产物并从你停下的地方继续。

想给现有变更添加更多产物？

/opsx:continue add-my-feature

基于已存在的内容显示什么已准备好创建。

需要查看状态？

openspec status --change add-my-feature

新配置系统

config.yaml 结构

# Required: Default schema for new changes
schema: spec-driven

# Optional: Project context (max 50KB)
# Injected into ALL artifact instructions
context: |
  Your project background, tech stack,
  conventions, and constraints.

# Optional: Per-artifact rules
# Only injected into matching artifacts
rules:
  proposal:
    - Include rollback plan
  specs:
    - Use Given/When/Then format
  design:
    - Document fallback strategies
  tasks:
    - Break into 2-hour maximum chunks

Schema 解析

当确定使用哪个 Schema 时，OPSX 按顺序检查：

  1. CLI 标志：--schema <name>（最高优先级）
  2. 变更元数据：变更目录中的 .openspec.yaml
  3. 项目配置：openspec/config.yaml
  4. 默认值：spec-driven

可用 Schema

Schema 产物 适用于
spec-driven proposal → specs → design → tasks 大多数项目

列出所有可用的 Schema：

openspec schemas

自定义 Schema

创建你自己的工作流：

openspec schema init my-workflow

或 fork 一个现有的：

openspec schema fork spec-driven my-workflow

参见自定义配置了解详情。

故障排除

"Legacy files detected in non-interactive mode"

你在 CI 或非交互式环境中运行。使用：

openspec init --force

迁移后命令不出现

重启你的 IDE。技能在启动时检测。

"Unknown artifact ID in rules"

检查你的 rules: 键是否匹配你的 Schema 的产物 ID：

  • spec-driven：proposal, specs, design, tasks

运行这个查看有效的产物 ID：

openspec schemas --json

配置没有生效

  1. 确保文件在 openspec/config.yaml（不是 .yml）
  2. 验证 YAML 语法
  3. 配置更改立即生效——不需要重启

project.md 没有被迁移

系统有意保留 project.md，因为它可能包含你的自定义内容。手动审查它，将有用的部分移动到 config.yaml，然后删除它。

想看看什么会被清理？

运行 init 并拒绝清理提示——你会看到完整的检测摘要，不会做任何更改。
