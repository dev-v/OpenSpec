OPSX 工作流

OpenSpec 的标准工作流——流动而非僵化的迭代工作方式

欢迎在 Discord 上提供反馈。

它是什么？

OPSX 现在是 OpenSpec 的标准工作流。

它是一个流动的、迭代的工作流用于 OpenSpec 变更。不再有僵硬的阶段——只有你可以随时执行的动作。

为什么存在

旧版 OpenSpec 工作流可用，但它是锁定的：

  • 指令是硬编码的——埋在 TypeScript 中，你无法更改
  • 全部或全无——一个大命令创建一切，无法测试单个部分
  • 固定结构——每个人都用同样的工作流，无法自定义
  • 黑盒——当 AI 输出不好时，你无法微调提示

OPSX 打开了它。现在任何人都可以：

  1. 试验指令——编辑一个模板，看看 AI 是否做得更好
  2. 逐粒度测试——独立验证每个制品的指令
  3. 自定义工作流——定义你自己的制品和依赖
  4. 快速迭代——改一个模板，立即测试，无需重新构建
旧版工作流:                      OPSX:
┌────────────────────────┐           ┌────────────────────────┐
│  Hardcoded in package  │           │  schema.yaml           │◄── 你编辑这个
│  (can't change)        │           │  templates/*.md        │◄── 或这个
│        ↓               │           │        ↓               │
│  Wait for new release  │           │  Instant effect        │
│        ↓               │           │        ↓               │
│  Hope it's better      │           │  Test it yourself      │
└────────────────────────┘           └────────────────────────┘

这适用于所有人：

  • 团队——创建匹配你实际工作方式的工作流
  • 高级用户——微调提示以在你的代码库上获得更好的 AI 输出
  • OpenSpec 贡献者——无需发布即可试验新方法

我们仍在学习什么效果最好。OPSX 让我们一起学习。

用户体验

线性工作流的问题：

你在"规划阶段"，然后在"实现阶段"，然后"完成"。但实际工作不是这样的。你实现了一些东西，发现设计有误，需要更新规格，继续实现。线性阶段与实际工作方式相悖。

OPSX 方法：

  • 动作，而非阶段——创建、实现、更新、归档——随时做任何一个
  • 依赖是使能器——它们显示什么可能，而非下一步必需什么
  proposal ──→ specs ──→ design ──→ tasks ──→ implement

设置

# 确保安装了 openspec — skills 会自动生成
openspec init

这会在 .claude/skills/（或等效位置）中创建 AI 编码助手自动检测的技能。

默认情况下，OpenSpec 使用 core 工作流 profile（propose、explore、apply、sync、archive）。如果你想要扩展工作流命令（new、continue、ff、verify、bulk-archive、onboard），用 openspec config profile 配置并用 openspec update 应用。

设置期间，你会被提示创建项目配置（openspec/config.yaml）。这是可选但推荐的。

项目配置

项目配置让你设置默认值并将项目特定上下文注入所有制品。

创建配置

配置在 openspec init 期间创建，或手动创建：

# openspec/config.yaml
schema: spec-driven

context: |
  Tech stack: TypeScript, React, Node.js
  API conventions: RESTful, JSON responses
  Testing: Vitest for unit tests, Playwright for e2e
  Style: ESLint with Prettier, strict TypeScript

rules:
  proposal:
    - Include rollback plan
    - Identify affected teams
  specs:
    - Use Given/When/Then format for scenarios
  design:
    - Include sequence diagrams for complex flows

配置字段

字段类型描述
schemastring新变更的默认模式（例如 spec-driven）
contextstring注入到所有制品指令中的项目上下文
rulesobject按制品的规则，以制品 ID 为键

如何工作

模式优先级（从高到低）：

  1. CLI 标志（--schema <name>）
  2. 变更元数据（变更目录中的 .openspec.yaml）
  3. 项目配置（openspec/config.yaml）
  4. 默认（spec-driven）

上下文注入：

  • 上下文被预置到每个制品的指令前
  • 用 <context>...</context> 标签包裹
  • 帮助 AI 理解你项目的约定

规则注入：

  • 规则仅为匹配的制品注入
  • 用 <rules>...</rules> 标签包裹
  • 出现在上下文之后、模板之前

按模式的制品 ID

spec-driven（默认）：

  • proposal——变更提案
  • specs——规格
  • design——技术设计
  • tasks——实现任务

配置验证

  • rules 中的未知制品 ID 会生成警告
  • 模式名称会对照可用模式验证
  • 上下文有 50KB 大小限制
  • 无效 YAML 会带行号报告

故障排除

"Unknown artifact ID in rules: X"

  • 检查制品 ID 是否匹配你的模式（参见上面的列表）
  • 运行 openspec schemas --json 查看每个模式的制品 ID

配置未应用：

  • 确保文件在 openspec/config.yaml（不是 .yml）
  • 用验证器检查 YAML 语法
  • 配置更改立即生效（无需重启）

上下文太大：

  • 上下文限制为 50KB
  • 改为总结或链接到外部文档

命令

命令作用
/opsx:propose创建变更并一步生成规划制品（默认快速路径）
/opsx:explore思考想法、调查问题、澄清需求
/opsx:new开始新变更脚手架（扩展工作流）
/opsx:continue创建下一个制品（扩展工作流）
/opsx:ff快进规划制品（扩展工作流）
/opsx:apply实现任务，按需更新制品
/opsx:update修改变更的规划制品并保持一致
/opsx:verify验证实现是否匹配制品（扩展工作流）
/opsx:sync将增量规格同步到主规格（默认工作流，可选）
/opsx:archive完成后归档
/opsx:bulk-archive归档多个已完成变更（扩展工作流）
/opsx:onboard端到端变更的引导式演练（扩展工作流）

使用

探索一个想法

/opsx:explore

思考想法、调查问题、比较选项。不需要结构——就是一个思考伙伴。当洞察明确后，转入 /opsx:propose（默认）或 /opsx:new//opsx:ff（扩展）。

开始新变更

/opsx:propose

创建变更并生成实现前所需的规划制品。

如果你已启用扩展工作流，可以改为使用：

/opsx:new        # 仅脚手架
/opsx:continue   # 一次创建一个制品
/opsx:ff         # 一次创建所有规划制品

创建制品

/opsx:continue

基于依赖关系显示什么准备好创建，然后创建一个制品。重复使用以逐步构建你的变更。

/opsx:ff add-dark-mode

一次创建所有规划制品。当你清楚要构建什么时使用。

实现（流动部分）

/opsx:apply

遍历任务，边走边勾选。如果你同时处理多个变更，可以运行 /opsx:apply <name>；否则它应该从对话中推断并在无法确定时提示你选择。

更新变更

/opsx:update add-dark-mode - we're storing the theme in a cookie now

修改变更的现有规划制品并保持一致——在任何方向（设计编辑可能波及回提案）。仅限规划制品：它从不编辑代码，也从不创建缺少的制品（那是 /opsx:continue）。每个编辑都先与你确认。如果变更已实现，它推荐 /opsx:apply 让代码跟上修改后的计划。如果你的修改改变了变更的意图，改为重新开始——参见何时更新 vs. 开始新变更。

完成

/opsx:archive   # 完成后移到归档（如需要会提示同步规格）

何时更新 vs. 开始新变更

你总可以在实现前编辑提案或规格。但什么时候精炼变成了"这是不同的工作"？

提案捕获什么

一个提案定义三件事：

  1. 意图——你在解决什么问题？
  2. 范围——什么在/不在界限内？
  3. 方案——你将如何解决？

问题是：哪个变了，变了多少？

在以下情况更新现有变更：

相同意图，精炼的执行

  • 你发现了之前未考虑的边界情况
  • 方案需要微调但目标不变
  • 实现发现设计略有偏差

范围缩小

  • 你意识到完整范围太大，想先交付 MVP
  • "添加暗色模式" → "添加暗色模式切换（系统偏好在 v2 中）"

学习驱动的修正

  • 代码库结构不是你以为的那样
  • 一个依赖不像预期那样工作
  • "使用 CSS 变量" → "改用 Tailwind 的 dark: 前缀"

在以下情况开始新变更：

意图根本改变

  • 问题本身现在不同了
  • "添加暗色模式" → "添加带自定义颜色、字体、间距的综合主题系统"

范围爆炸

  • 变更增长太多，本质上是不同的工作
  • 更新后原始提案将面目全非
  • "修复登录 bug" → "重写认证系统"

原始可以完成

  • 原始变更可以标记为"完成"
  • 新工作独立，不是精炼
  • 完成"添加暗色模式 MVP" → 归档 → 新变更"增强暗色模式"

启发式规则

                        ┌─────────────────────────────────────┐
                        │     Is this the same work?          │
                        └──────────────┬──────────────────────┘
                                       │
                    ┌──────────────────┼──────────────────┐
                    │                  │                  │
                    ▼                  ▼                  ▼
             Same intent?      >50% overlap?      Can original
             Same problem?     Same scope?        be "done" without
                    │                  │          these changes?
                    │                  │                  │
          ┌────────┴────────┐  ┌──────┴──────┐   ┌───────┴───────┐
          │                 │  │             │   │               │
         YES               NO YES           NO  NO              YES
          │                 │  │             │   │               │
          ▼                 ▼  ▼             ▼   ▼               ▼
       UPDATE            NEW  UPDATE       NEW  UPDATE          NEW
测试更新新变更
身份"同一件事，精炼""不同的工作"
范围重叠>50% 重叠<50% 重叠
完成性没有这些变更就不能"完成"可以完成原始的，新工作独立
叙事更新链讲述连贯的故事补丁会比解释更令人困惑

原则

更新保留上下文。新变更提供清晰。

当你的思考历史有价值时选择更新。当重新开始比修补更清晰时选择新建。

把它想象成 git 分支：

  • 在同一功能上工作时继续提交
  • 当是真正的新工作时开始一个新分支
  • 有时合并部分功能并为第二阶段重新开始

有什么不同？

旧版（/openspec:proposal）OPSX（/opsx:*）
结构一个大提案文档有依赖关系的离散制品
工作流线性阶段：规划 → 实现 → 归档流动动作——随时做任何事
迭代回去很尴尬随学习更新制品
自定义固定结构模式驱动（定义自己的制品）

关键洞察：工作不是线性的。OPSX 不再假装它是。

架构深入

本节解释 OPSX 在底层如何工作以及它与旧版工作流的比较。

本节的示例使用扩展命令集（new、continue 等）；默认 core 用户可以将同样的流程映射到 propose → apply → sync → archive。

哲学：阶段 vs 动作

┌─────────────────────────────────────────────────────────────────────────────┐
│                         旧版工作流                                          │
│                    （阶段锁定，全部或全无）                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ┌──────────────┐      ┌──────────────┐      ┌──────────────┐             │
│   │   PLANNING   │ ───► │ IMPLEMENTING │ ───► │   ARCHIVING  │             │
│   │    PHASE     │      │    PHASE     │      │    PHASE     │             │
│   └──────────────┘      └──────────────┘      └──────────────┘             │
│         │                     │                     │                       │
│         ▼                     ▼                     ▼                       │
│   /openspec:proposal   /openspec:apply      /openspec:archive              │
│                                                                             │
│   • 一次创建所有制品                                                       │
│   • 实现期间无法回去更新规格                                               │
│   • 阶段门强制线性推进                                                     │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘


┌─────────────────────────────────────────────────────────────────────────────┐
│                            OPSX 工作流                                      │
│                      （流动动作，迭代）                                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│              ┌────────────────────────────────────────────┐                 │
│              │           ACTIONS (not phases)             │                 │
│              │                                            │                 │
│              │   new ◄──► continue ◄──► apply ◄──► archive │                 │
│              │    │          │           │           │    │                 │
│              │    └──────────┴───────────┴───────────┘    │                 │
│              │              any order                     │                 │
│              └────────────────────────────────────────────┘                 │
│                                                                             │
│   • 一次创建一个制品或快进                                                │
│   • 实现期间更新规格/设计/任务                                            │
│   • 依赖推动进展，阶段不存在                                               │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

组件架构

旧版工作流使用 TypeScript 中的硬编码模板：

┌─────────────────────────────────────────────────────────────────────────────┐
│                      旧版工作流组件                                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Hardcoded Templates (TypeScript strings)                                  │
│                    │                                                        │
│                    ▼                                                        │
│   Tool-specific configurators/adapters                                      │
│                    │                                                        │
│                    ▼                                                        │
│   Generated Command Files (.claude/commands/openspec/*.md)                  │
│                                                                             │
│   • 固定结构，无制品感知                                                   │
│   • 变更需要代码修改 + 重新构建                                            │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

OPSX使用外部模式和依赖图引擎：

┌─────────────────────────────────────────────────────────────────────────────┐
│                         OPSX 组件                                           │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Schema Definitions (YAML)                                                 │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  name: spec-driven                                                  │   │
│   │  artifacts:                                                         │   │
│   │    - id: proposal                                                   │   │
│   │      generates: proposal.md                                         │   │
│   │      requires: []              ◄── 依赖                             │   │
│   │    - id: specs                                                      │   │
│   │      generates: specs/**/*.md  ◄── Glob 模式                        │   │
│   │      requires: [proposal]      ◄── proposal 后启用                   │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                    │                                                        │
│                    ▼                                                        │
│   Artifact Graph Engine                                                     │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  • Topological sort (dependency ordering)                           │   │
│   │  • State detection (filesystem existence)                           │   │
│   │  • Rich instruction generation (templates + context)                │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                    │                                                        │
│                    ▼                                                        │
│   Skill Files (.claude/skills/openspec-*/SKILL.md)                          │
│                                                                             │
│   • 跨编辑器兼容 (Claude Code, Cursor, Windsurf)                            │
│   • Skills 查询 CLI 获取结构化数据                                          │
│   • 通过模式文件完全可自定义                                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

                           specs, design)

迭代模型

旧版工作流——迭代尴尬：

  ┌─────────┐     ┌─────────┐     ┌─────────┐
  │/proposal│ ──► │ /apply  │ ──► │/archive │
  └─────────┘     └─────────┘     └─────────┘
       │               │
       │               ├── "Wait, the design is wrong"
       │               │
       │               ├── Options:
       │               │   • Edit files manually (breaks context)
       │               │   • Abandon and start over
       │               │   • Push through and fix later
       │               │
       │               └── No official "go back" mechanism
       │
       └── Creates ALL artifacts at once

OPSX——自然迭代：

  /opsx:new ───► /opsx:continue ───► /opsx:apply ───► /opsx:archive
      │                │                  │
      │                │                  ├── "The design is wrong"
      │                │                  │
      │                │                  ▼

自定义模式

使用模式管理命令创建自定义工作流：

# 从头创建新模式（交互式）
openspec schema init my-workflow

# 或 fork 现有模式作为起点
openspec schema fork spec-driven my-workflow

# 验证你的模式结构
openspec schema validate my-workflow

# 查看模式从哪里解析（用于调试）
openspec schema which my-workflow

模式存储在 openspec/schemas/（项目本地，版本控制）或 ~/.local/share/openspec/schemas/（用户全局）。

模式结构：

openspec/schemas/research-first/
├── schema.yaml
└── templates/
    ├── research.md
    ├── proposal.md
    └── tasks.md

示例 schema.yaml：

name: research-first
artifacts:
  - id: research        # Added before proposal
    generates: research.md
    requires: []

  - id: proposal
    generates: proposal.md
    requires: [research]  # Now depends on research

  - id: tasks
    generates: tasks.md
    requires: [proposal]

依赖图：

   research ──► proposal ──► tasks

总结

方面旧版OPSX
模板硬编码 TypeScript外部 YAML + Markdown
依赖无（全部一次性）带拓扑排序的 DAG
状态基于阶段的心智模型文件系统存在性
自定义编辑源代码，重新构建创建 schema.yaml
迭代阶段锁定流动，编辑任何东西
编辑器支持工具特定配置器/适配器单一 skills 目录

模式

模式定义存在哪些制品及其依赖。当前可用：

  • spec-driven（默认）：proposal → specs → design → tasks
# 列出可用模式
openspec schemas

# 查看所有模式及其解析来源
openspec schema which --all

# 交互式创建新模式
openspec schema init my-workflow

# Fork 现有模式进行自定义
openspec schema fork spec-driven my-workflow

# 使用前验证模式结构
openspec schema validate my-workflow

提示

  • 在提交变更前用 /opsx:explore 思考一个想法
  • 清楚要什么时用 /opsx:ff，探索时用 /opsx:continue
  • 在 /opsx:apply 期间，如果有问题——修复制品，然后继续
  • 任务通过 tasks.md 中的复选框跟踪进度
  • 随时检查状态：openspec status --change "name"
