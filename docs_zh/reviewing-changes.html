审查变更

在编写任何代码之前，花两分钟检查 AI 起草的计划

OpenSpec 的全部承诺在于：你和你的 AI 在编写任何代码之前就构建什么达成一致。这个协议只有在你真正阅读了 AI 起草的内容后才具有实际意义。本页讲述的就是你做这件事的那两分钟——打开什么、按什么顺序、寻找什么。

道理很简单：在一段话的计划中抓住一个错误方向几乎不花成本。而在 300 行代码中抓住同样的错误方向则代价不菲。审查就是你收回这笔投资的时刻。

你审查的两个时刻

恰好有两个时刻：

/opsx:propose ──► 审查计划 ──► /opsx:apply ──► 审查代码 ──► /opsx:archive
                  (在编写代码之前)                    (/opsx:verify)
  1. 在 /opsx:propose 之后（或 /opsx:ff），在 /opsx:apply 之前——趁计划还只是文字时阅读它。
  2. 在构建完成后，使用 /opsx:verify——检查代码是否真正执行了计划所说的内容。

第一次审查是为你节省最多的那次，也是人们最容易跳过的那次。本页大部分篇幅都在讲它。

按此顺序阅读

一个变更就是 openspec/changes/<name>/ 中的一组纯 Markdown 文件。按能让你最早发现问题就停下来的顺序阅读：

openspec/changes/add-dark-mode/
├── proposal.md      1. 意图和范围   ← 如果这里错了，到此为止
├── specs/…/spec.md  2. 需求         ← 审查的核心
├── design.md        (仅适用于较大的变更) — 技术方案
└── tasks.md         3. 工作计划

你不需要逐行阅读。你需要回答三个问题，每个文件一个。

提案：这是正确的问题吗？

首先打开 proposal.md。它记录了"为什么"和"什么"——意图、范围、一两段话的方案。

好的样子：一个清晰的意图，一个你认可的范围，以及一个值得现在做的理由。

危险信号：

  • 它解决的问题与你要求解决的略有不同。
  • 范围扩大了——你要求一个主题切换，提案却"顺便"也涉及了认证功能。
  • 含糊不清。"改进设置页面"不是范围；"添加一个尊重操作系统偏好的暗色模式切换"才是。

要回答的问题：这是否与我实际要求的一致？有没有什么东西悄悄混进来了？如果答案是否定的，停下来——不要继续往下读，修改提案（参见反馈修正）。

规格增量："完成"定义正确吗？

这是审查的核心。specs/ 下的增量规格说明了变更交付后什么是真实的——以需求和证明需求的场景来表述：

## ADDED Requirements

### Requirement: Dark Mode Toggle
The system SHALL let a user switch between light and dark themes.

#### Scenario: Respects the OS preference on first load
- GIVEN a user who has never set a theme
- WHEN they open the app on a device set to dark mode
- THEN the app renders in dark mode

好的需求是什么样的：一个清晰的 SHALL/MUST 声明，你可以交给测试人员，至少一个场景的 GIVEN/WHEN/THEN 真正验证了该声明。

危险信号：

  • 含糊的需求。"系统 SHALL 快速"无法构建或测试。什么是快速？
  • 没有场景的需求，或者场景没有测试它所在的需求。
  • 最有价值的发现：遗漏了什么。AI 忠实地写下你说的。你的工作是注意到你忘了说的。如果你最关心操作系统偏好的场景而没有场景提到它，这就是审查在发挥作用。

阅读增量时问自己如果系统恰好做了——而且只做了——这些，我会满意吗？这里还没有涉及代码，所以修改成本很低。

任务：工作计划合理吗？

最后打开 tasks.md。它是 AI 将要执行的实施清单。

好的样子：有序的步骤，每一步可追溯到需求，没有神秘内容。

危险信号：

  • 一个任务没有对应的需求（它从哪来的？）。
  • 一个巨大的"实现功能"任务隐藏了所有真正的决策。
  • 一个任务涉及你刚刚批准的范围之外的东西。

你不是在做估算或微管理——你在检查计划是否匹配你已经接受的需求。

反馈修正成本很低

如果三个问题中任何一个的答案不对，直接说出来。没有阶段也没有什么被锁定——你修复它然后继续。两种方式，正如编辑变更中所述：

  • 自己编辑文件。它是纯 Markdown；修改范围行，收紧需求，删除任务。
  • 告诉 AI 哪里不对让它修改："去掉认证变更——超出范围"，"为用户已选择主题的情况添加一个场景"，"把任务 3 拆分为 schema 和 UI"。

然后重新阅读你修改的部分。反复修改直到你愿意签名的计划。这种来回就是产品在运作。

代码完成后：验证

工作构建完成后，/opsx:verify 是你的第二次审查。它会重新阅读制品和代码，并在三个维度上报告不匹配之处：

维度检查内容
完整性每个任务都已完成，每个需求都已实现，场景已覆盖
正确性实现与规格意图匹配，边界情况已处理
一致性设计决策真正体现在代码中
 
You: /opsx:verify

AI:  Verifying add-dark-mode...

     COMPLETENESS
     ✓ All 8 tasks in tasks.md are checked
     ✓ All requirements in specs have corresponding code
     ⚠ Scenario "Respects the OS preference on first load" has no test coverage

它将问题标记为 CRITICAL、WARNING 或 SUGGESTION，并且不会阻止归档——它会揭示差距并把决定权留给你。这就是"AI 是否编写了代码"和"AI 是否构建了我们商定的内容"之间的区别。

/opsx:verify 属于扩展配置。如果你没有它，用 openspec config profile（然后 openspec update）开启，或者自己重新阅读变更和代码差异。

审查的力度要适当

不是每个变更都值得完整的审查流程。一个单文件错别字修复只需要 20 秒的扫视。涉及认证、支付或不可恢复数据的变更值得上面每一个问题。重点从来不是仪式感——而是把注意力花在出错代价高的地方，在不会出错的地方快速浏览。

两分钟清单

  • ☐ 提案的意图与我要求的一致。
  • ☐ 范围中没有悄悄混入额外内容。
  • ☐ 每个需求都足够具体，可以测试。
  • ☐ 每个需求都有一个真正验证它的场景。
  • ☐ 我最关心的场景已被覆盖。
  • ☐ 任务映射到需求；没有神秘或超范围的内容。
  • ☐ 如果 AI 恰好构建这个而且只构建这个，我会感到满意。

如果七项全部通过，放心运行 /opsx:apply。如果任何一项失败，那不是挫折——而是这两分钟在发挥作用。
