Stores：在独立仓库中规划

跨仓库协作的 Beta 功能指南

Beta。Stores、references、working context 和 worksets 是新功能。命令名、标志、文件格式和 JSON 输出在版本间可能仍有变化。下面的每个演练都是针对当前构建运行的，但升级后请重新阅读本指南。

解决什么问题

OpenSpec 通常存在于一个代码仓库内：一个 openspec/ 文件夹与你的代码并列，存放该仓库的规格和变更。

当你的规划超出一个仓库时就不再适用了：

  • 你的工作跨多个仓库——一个功能涉及 API 服务器、Web 应用和共享库。计划应该放在谁的 openspec/ 文件夹中？
  • 你的团队在代码存在之前规划，或规划永远不会成为这个仓库中的代码的内容。
  • 需求由一个团队拥有，被其他团队消费。Wiki 版本漂移，而且你的编码代理反正也读不了它。

Store 就是答案：一个独立的仓库，其全部职责就是规划。它有你已经熟悉的 openspec/ 结构——规格和变更——加上一个小的身份文件。你在你的机器上按名称注册一次，然后每个正常的 OpenSpec 命令都可以从任何地方在其中工作。

结构

            team-plans  (a store: planning in its own repo)
            ├── .openspec-store/store.yaml     identity: "I am team-plans"
            └── openspec/
                ├── specs/      what is true
                └── changes/    what is in motion
                      ▲
                      │ registered on each machine by name;
                      │ shared by pushing/cloning like any repo
        ┌─────────────┼─────────────┐
        │             │             │
    web-app       api-server     mobile-app
   (code repo)   (code repo)    (code repo)

两条规则使这保持简单：

  1. Store 就是一个 git 仓库。 你自己提交、推送、拉取和审查它。OpenSpec 从不自行克隆、同步或推送。
  2. 声明，不是机制。 仓库可以声明它们与 stores 的关系（如下所示）。声明改变 OpenSpec 能告诉你的内容——从不改变你的命令在哪里执行。

五分钟创建你的第一个 store

两个命令从零到可用的、store 范围的变更：

openspec store setup team-plans --path ~/openspec/team-plans

Store ready: team-plans
Location: /Users/you/openspec/team-plans
OpenSpec root: ready
Registry: registered

Next: run normal OpenSpec commands against this store, for example:
  openspec new change <change-id> --store team-plans
Share this store by committing and pushing it like any Git repo.

openspec new change add-login --store team-plans

Using OpenSpec root: team-plans (/Users/you/openspec/team-plans)
Created change 'add-login' at /Users/you/openspec/team-plans/openspec/changes/add-login/
Schema: spec-driven
Next: openspec status --change add-login --store team-plans

这就是整个模型。从这里开始，生命周期完全是你所知道的——status、instructions、validate、archive——每个命令加上 --store team-plans，每个打印的提示都为你带上了标志。Using OpenSpec root: 行总是告诉你命令在哪里执行。

故事：一个团队，一个规划仓库

一个团队将其规格和变更放在 team-plans 中，而不是分散在代码仓库中。

第一天（谁设置它）：

openspec store setup team-plans --path ~/openspec/team-plans \
  --remote git@github.com:acme/team-plans.git
git -C ~/openspec/team-plans push -u origin main

传递 --remote 会将克隆 URL 记录在 store 自己的身份文件（.openspec-store/store.yaml）中，放在初始提交里。每个未来的克隆一出生就知道它来自哪里，所以健康检查和错误消息可以为还没有它的队友打印一个完整的、可粘贴的修复命令。

每个队友（每台机器一次）：

git clone git@github.com:acme/team-plans.git ~/openspec/team-plans
openspec store register ~/openspec/team-plans

从那以后，每个人按名称在同一个规划仓库中工作：

openspec status --store team-plans --change add-login
openspec show add-login --store team-plans

共享工作就是 git，这是有意为之的。你创建的变更只存在于你的检出中，直到你提交并推送它——和代码一样。计划免费获得分支、pull request 和审查，因为 store 是一个普通仓库。

连接团队的代码仓库。一个规划完全外部化的代码仓库只需要一行，在 openspec/config.yaml 中：

# web-app/openspec/config.yaml
store: team-plans

现在在 web-app 中运行的每个 OpenSpec 命令都对 team-plans 执行，完全不需要标志：

cd ~/src/web-app
openspec status --change add-login

Using OpenSpec root: team-plans (/Users/you/openspec/team-plans)
...

指针是一个回退，从不覆盖：显式的 --store 总是优先，如果仓库发展出自己真正的规划文件夹，那些优先（并警告移除过时的指针）。

故事：跨团队线的需求

平台团队拥有需求。产品团队在各自的仓库中、用自己的设计来构建。reference 描述了这种关系，而不移动任何人的工作。

   platform-reqs (store)                 api-server (code repo)
   owned by the platform team            owned by a product team
   ┌──────────────────────────┐          ┌──────────────────────────┐
   │ openspec/specs/          │ ◀────────│ openspec/config.yaml     │
   │   payments/spec.md       │ reads    │   references:            │
   │   auth/spec.md           │          │     - platform-reqs      │
   │                          │          │ openspec/specs/          │
   │ openspec/changes/        │          │   (their own designs)    │
   │   platform work          │          │ openspec/changes/        │
   │                          │          │   (their own work)       │
   │                          │          └──────────────────────────┘
   └──────────────────────────┘

产品团队在它的仓库的 openspec/config.yaml 中声明它依赖什么：

references:
  - platform-reqs

References 是只读上下文。仓库保持自己的 openspec/ 根；工作留在那里。变化是：该仓库中的 openspec instructions 现在包含被引用 store 的规格索引——每个都有一行摘要和确切的获取命令（openspec show <spec-id> --type spec --store platform-reqs）。在 api-server 中工作的代理可以找到上游支付需求，引用它们，并在仓库自己的根中编写低级设计——无需任何人粘贴上下文。

一个 reference 可以携带其克隆来源，所以还没有该 store 的队友得到一个完整的修复而不是一个死胡同：

references:
  - { id: platform-reqs, remote: "git@github.com:acme/platform-reqs.git" }

当你想计划和代码一起打开时，创建一个 workset。 这是个人和显式的：每个人选择他们实际在机器上工作的文件夹。关于这些本地检出路径的任何内容都不会提交到共享规划仓库。

openspec workset create platform \
  --member ~/openspec/platform-reqs \
  --member ~/src/api-server \
  --member ~/src/web-app

你总是可以问的两个问题

"我的设置健康吗？" — openspec doctor 检查当前根和它引用的 stores，只读，每个发现附带可粘贴的修复：

Doctor

Root
  Location: /Users/you/src/api-server
  OpenSpec root: ok

References
  - platform-reqs: ok (/Users/you/openspec/platform-reqs)
  - design-system: Referenced store 'design-system' is not registered on this machine.
    Fix: git clone -- git@github.com:acme/design-system.git '/Users/you/openspec/design-system' && openspec store register '/Users/you/openspec/design-system' --id design-system

"我在处理什么？" — openspec context 从 OpenSpec 声明中组装工作集：根和它引用的 stores。

Working context for api-server (/Users/you/src/api-server)

OpenSpec root
  api-server  /Users/you/src/api-server

Referenced stores
  platform-reqs  /Users/you/openspec/platform-reqs
    Fetch: openspec show <spec-id> --type spec --store platform-reqs

两者都支持 --json 供代理使用。openspec context --code-workspace <path> 额外写入一个包含整个集合的 VS Code 工作区文件——这是此命令执行的唯一写入操作。

Worksets：重新打开你一起工作的文件夹

独立于上述所有：大多数人每次会话都会一起打开相同的几个文件夹——规划仓库加两三个代码仓库。workset 是一个个人的、命名的视图，正是为此设计的，用一条命令在你选择的工具中重新打开。

  workset "platform"                 openspec workset open platform
  ├── team-plans   ~/openspec/team-plans         │
  ├── api-server   ~/src/api-server              ▼
  └── web-app      ~/src/web-app       all three open in your tool

openspec workset create platform \
  --member ~/openspec/team-plans --member ~/src/api-server \
  --tool code
openspec workset list

platform  (opens in VS Code)
  team-plans  /Users/you/openspec/team-plans
  api-server  /Users/you/src/api-server

openspec workset open platform 然后启动保存的工具：编辑器（VS Code、Cursor）打开一个窗口包含每个成员并返回。第一个成员是主要的。随时用 --tool <id> 覆盖工具。

Worksets 是有意不共享的状态。它们存在于你的机器上，从不提交，不对工作做任何声明——它们只记录你喜欢一起打开的内容。删除一个从不触及成员文件夹。新工具是配置，不是代码：任何可以通过工作区文件或每文件夹附加标志启动的东西都可以在全局配置（openspec config edit）的 openers 键下添加。

命令如何决定在哪里执行

每个正常命令以相同的方式、按以下顺序解析其根：

1. --store <id>          you said so explicitly        → that store
2. nearest openspec/     a real planning root here     → this repo
   (walking up from cwd)
3. store: pointer        config.yaml declares a store  → that store
4. none of the above     stores registered on this     → error with a
                         machine?                        selection hint
                         no stores registered?         → the current
                                                          directory
                                                          (classic behavior)

Using OpenSpec root: 行（以及 --json 输出中的 root 块）告诉你处于哪种情况。

已知限制

  • Beta 状态。本页面上的所有内容可能在版本间变化——名称、标志、文件格式、JSON 键。
  • 每台机器每个 store id 一个检出。在同一 id 下注册第二个检出会失败，提示先 store unregister。
  • 从不同步——这是设计。OpenSpec 从不克隆、拉取或推送。一个过时的检出显示过时的规格直到你拉取；references 从磁盘上的内容实时索引。
  • 空规划文件夹可以不存在。一个新 store 可能还没有 openspec/changes/、openspec/specs/ 或 openspec/changes/archive/。这在 Beta 期间是可接受的；一旦正常命令为它们创建文件，这些文件夹就会出现。
  • 指针仓库保持指针。一个仅配置的仓库，其 openspec/config.yaml 声明了 store: <id>，被视为外部化的规划，而不是要注册的 store 检出。如果你有意想将该仓库转换为本地 store 根，请先移除 store: 行。
  • 某些命令留在原地。view、templates、schemas 和已弃用的名词形式（openspec change show...）只在当前目录上操作——没有 --store。
  • 每机器状态是每机器的。Store 注册表和 worksets 是本地设置。关于你机器布局的任何内容都不会提交到共享规划。
  • Worksets 的两种启动风格。一个不能用工作区文件或每文件夹附加标志启动的工具不能被添加为 opener。
  • Agent JSON 有已知的命名大小写分歧（store 系列键是 snake_case，workflow 系列是 camelCase）。在agent 契约中文档化；统一推迟到版本化发布。

东西在哪里

内容 位置 共享？
Store 的规划 <store>/openspec/（specs, changes） 是——提交并推送它
Store 的身份 <store>/.openspec-store/store.yaml 是——与 store 一起提交
Store 注册表 <data dir>/openspec/stores/registry.yaml 否——仅此机器
Worksets <data dir>/openspec/worksets/ 否——仅此机器

<data dir> 在 macOS 和 Linux 上是 ~/.local/share/openspec（或设置了 $XDG_DATA_HOME/openspec 时），在 Windows 上是 %LOCALAPPDATA%\openspec。
