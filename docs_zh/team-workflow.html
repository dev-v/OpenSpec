团队协作

OpenSpec 在团队中的使用：规格说明放在哪里，如何在 PR 中审查，以及如何融入你现有的工作流

其他指南中的所有内容，无论你是独立工作还是在 20 人的团队中，工作方式都一样。在团队中变化的是边缘性的问题：规格说明放在哪里，团队成员如何审查计划，以及这些如何融入我们已有的拉取请求流程？

简短回答：一个变更就是文件，而 OpenSpec 从不触碰 git。所以它融入你现有的工作流而不是取代它。本页说明了行之有效的约定。

一条规则：OpenSpec 不触碰 git

OpenSpec 在 openspec/ 下读取和写入纯 Markdown。它从不在你的项目中提交、分支、推送或拉取——也从不自行克隆或同步store。这意味着：

  • 你像对待任何源代码一样提交 openspec/。规格说明、活动变更和归档是你项目历史的一部分。（是的，提交整个文件夹——参见FAQ。）
  • 一个变更是你像代码一样版本控制的文件夹。openspec/changes/add-dark-mode/ 就是分支上的文件。
  • 以下所有都是约定，不是强制。OpenSpec 不会要求你这样做；它只是很自然地契合。

日常工作循环

行之有效的工作流将一个变更映射到一个分支和一个拉取请求：

git switch -c add-dark-mode        开始一个分支，照常
   │
/opsx:propose add-dark-mode        起草计划（提案 + 规格 + 任务）
   │
审查计划                            你在编写代码前阅读它——参见审查变更
   │
/opsx:apply                        构建它；制品 + 代码同时变更
   │
git commit && 打开 PR            PR 包含规格增量 AND 代码
   │
队友审查，合并
   │
/opsx:archive                      将增量折叠进 specs/，将变更移至 archive/

计划和代码并排存在于同一个分支中，因此你的队友同时审查两者，六个月后归档的规格仍然解释了代码为什么是这个样子。

在拉取请求中审查规格

这是团队感受到回报的地方。当 PR 包含变更的增量规格时，审查者获得了原始 diff 永远不会给他们的东西：一个用通俗语言描述这个变更应该做什么的声明，在他们阅读一行代码之前。

审查者的良好审查顺序：

  1. 阅读 proposal.md——这是正确的问题和范围吗？
  2. 阅读 specs/ 下的增量——"完成"定义正确吗？（这就是审查变更的两分钟审查，现在在 PR 中进行。）
  3. 然后阅读代码 diff——它是否恰好交付了那些需求？

一个不同意方案的审查者可以对着提案说出来，成本很低，而不是在 300 行代码中重新争论。把增量规格放在 PR 描述顶部附近，或指引审查者到变更文件夹，让他们从那里开始。

何时归档

归档将一个变更的增量折叠进你的主 openspec/specs/，并将变更文件夹移至 openspec/changes/archive/YYYY-MM-DD-<name>/。因为 specs/ 是共享的真相来源，在团队中时时机很重要。两种可行的约定：

  • PR 合并后归档（推荐）。分支承载活动变更；一旦它合并到你的主分支，就在那里归档（通常是一个小的后续提交或计划清理）。这确保共享的 specs/ 只随实际交付的工作前进。
  • 在 PR 内归档。对小团队更简单：添加代码的同一个 PR 也同步并归档。权衡是你的 specs/ diff 和代码 diff 同时落地，可能使 PR 更嘈杂。

选择一种并保持一致。无论哪种方式，/opsx:archive 都会检查任务是否完成并提议先同步，所以不会意外地半成品合并。

两人，并行变更

因为变更是独立的文件夹，它们不会冲突：

  • 不同变更，不同人——没问题。add-dark-mode 和 rate-limit-login 是不同分支上的不同文件夹；它们在归档前互不干扰。
  • 一个变更，一个负责人。两个人编辑同一个变更文件夹就像两个人编辑同一个文件一样冲突。保持一个变更为单一作者，或拆分为两个变更（又一个适当大小的理由）。
  • 冲突出现的唯一地方是 specs/。如果两个变更都修改同一个需求，归档第二个时会在 openspec/specs/…/spec.md 中冲突——像任何合并冲突一样解决，保留反映现实的那个需求。这很少见，而且这是一个特性：git 在告诉你两个变更对系统应该如何行为有不同意见。

当规划超出单个仓库时

以上所有内容都假设计划存在于代码仓库自己的 openspec/ 文件夹中，这是正确的默认选择。当你的规划真正跨多个仓库或团队——一个功能涉及三个服务，或需求由一个团队拥有而其他团队消费——这就是 beta stores 功能的用途：规划拥有自己的仓库，任何代码仓库都可以指向它。从Stores 用户指南开始。
