故障排除

具体问题的具体修复方案

具体问题的具体修复方案。每一条都命名一个症状，用一句话解释可能的原因，并给出修复方法。如果你在这里找不到你的问题，常见问题可能有帮助，Discord肯定有帮助。

安装和设置

openspec: command not found

CLI 没有安装，或者你的 shell 找不到它。全局安装并检查：

npm install -g @fission-ai/openspec@latest
openspec --version

如果安装了但仍然找不到，你的全局 npm bin 目录可能不在 PATH 中。运行 npm bin -g 查看全局二进制文件的位置，确保该路径在你的 shell 配置文件中。

"Requires Node.js 20.19.0 or higher"

OpenSpec 需要 Node 20.19.0+。检查你的版本并在需要时升级：

node --version

如果你使用 bun 安装 OpenSpec，注意 OpenSpec 仍然在 Node 上运行，所以无论如何你都需要在 PATH 中有 Node 20.19.0+。参见安装指南。

openspec init 没有配置我的 AI 工具

Init 会询问要设置哪些工具。如果你跳过了你的工具或想添加另一个，再运行一次，或使用非交互式形式：

openspec init --tools claude,cursor

完整的工具 ID 列表见支持的工具。使用 --tools all 配置所有工具，--tools none 跳过工具设置。

命令不出现

如果 /opsx:propose（或你的工具的等效命令）不出现或不起作用，按以下列表排查。它们按检查速度从快到慢排列。

  1. 你可能搞错了地方。 斜杠命令在 AI 助手的聊天中运行，而不是你的终端。如果你在 shell 中输入了 /opsx:propose，那就是问题所在。参见命令工作原理。
  2. 重新生成文件。 从你的项目根目录： 
    openspec update
    这会为你配置的每个工具重写技能和命令文件。
  3. 重启你的助手。 大多数工具在启动时扫描技能和命令。一个新窗口通常就能搞定。
  4. 确认文件存在。 对于 Claude Code，检查 .claude/skills/ 是否包含 openspec-* 文件夹。其他工具有自己的目录，全部列在支持的工具中。
  5. 检查你是否初始化了该项目。 技能是按项目写入的。如果你克隆了一个仓库或切换了文件夹，在那里运行 openspec init（或 openspec update）。
  6. 确认你的工具支持命令文件。 少数工具（Kimi CLI、ForgeCode、Mistral Vibe）不生成 opsx-* 命令文件；它们使用基于技能的调用。格式因工具而异：参见支持的工具和命令工作原理。

处理变更

"Change not found"

命令无法判断你指的是哪个变更。明确命名它，或检查有什么： 

openspec list                    # see active changes
/opsx:apply add-dark-mode        # name the change in chat

同时确认你在正确的项目目录中。

"No artifacts ready"

每个产物要么已经创建，要么在等待依赖项。查看什么在阻塞： 

openspec status --change <name>

然后先创建缺失的依赖项。记住顺序：proposal 启用 specs 和 design；specs 和 design 一起启用 tasks。

openspec validate 报告警告或错误

验证会检查你的规格说明和变更是否有结构性问题。阅读消息：它会命名文件和问题。

openspec validate <name>           # validate one item
openspec validate --all            # validate everything
openspec validate --all --strict   # stricter checks, good for CI

常见原因包括缺少必需章节（如没有场景的规格说明）或格式错误的 delta 头。修复文件并重新运行。CLI 参考文档了输出格式。

AI 创建了不完整或错误的产物

AI 没有足够的上下文。几个手段有帮助：

  • 在 openspec/config.yaml 中添加项目上下文，使你的技术栈和约定注入到每个请求中。参见自定义配置。
  • 添加按产物的 rules: 用于仅适用于例如规格说明的指导。
  • 在提议时给出更详细的描述。
  • 使用扩展的 /opsx:continue 一次创建一个产物并逐一审查，而不是用 /opsx:ff 一次性全部创建。

归档无法完成，或警告未完成的任务

归档不会因为未完成的任务而阻塞，但会警告你，因为归档通常意味着工作已完成。如果任务是有意保留的（你在归档部分变更），继续。否则先完成任务。归档还会提议将你的 delta 规格合并到主规格中（如果你还没有同步）；除非你有理由不这样做，否则选择是。

配置

我的 config.yaml 没有生效

三个常见嫌疑：

  1. 文件名错误。 必须是 openspec/config.yaml，而不是 .yml。
  2. 无效的 YAML。 用任何 YAML 验证器运行；CLI 也会报告带行号的语法错误。
  3. 你期望需要重启。 不需要。配置更改立即生效。

"Unknown artifact ID in rules: X"

rules: 下的一个键与你的 Schema 中的任何产物都不匹配。对于默认的 spec-driven Schema，有效的 ID 是 proposal、specs、design、tasks。查看任何 Schema 的 ID：

openspec schemas --json

"Context too large"

context: 字段限制为 50KB，这是有意为之的，因为它被注入到每个请求中。精简它，或链接到更长的文档而不是粘贴。精简的上下文也会产生更好、更快的结果。

"Schema not found"

你引用的 Schema 名称不存在。列出可用的并检查拼写：

openspec schemas                    # list available schemas
openspec schema which <name>        # see where a schema resolves from
openspec schema init <name>         # create a custom one

参见自定义配置。

从旧工作流迁移

"Legacy files detected in non-interactive mode"

你在 CI 或非交互式 shell 中运行，OpenSpec 发现有旧文件需要清理但无法提示你。自动批准：

openspec init --force

迁移后命令没出现

重启你的 IDE。技能在启动时检测。如果仍然不出现，运行 openspec update 并检查支持的工具中的文件位置。

我的旧 project.md 没有被迁移

那是有意为之的。OpenSpec 从不自动删除 project.md，因为它可能包含你写的上下文。将有用的部分移动到 config.yaml 的 context: 部分，然后自己删除它。迁移指南详细介绍了这个过程，包括一个你可以交给 AI 来做精炼的提示词。

仍然卡住了？

  • Discord： discord.gg/YctCnvvshC
  • GitHub Issues： github.com/Fission-AI/OpenSpec/issues
  • 从终端： openspec feedback "what went wrong" 会为你打开一个 issue。

当你报告问题时，请包含你的 OpenSpec 版本（openspec --version）、你的 Node 版本（node --version）、你的 AI 工具，以及确切的命令和输出。这会让帮助快得多。
